# Our stack and our parts

Never write again what one of our parts already does. Use the part, pinned to its latest release,
and when it falls short, extend it in its own repository and release it.

## The parts

Every repository of the parts owner — `GROUNDWORK_OWNER`, else the signed-in `gh` user — with the `our-part` topic, its latest release (or its
newest tag when it has none) as the version to pin. The table is generated by
`global/catalog.mjs` in groundwork and refreshed on this machine once a day; a new part needs only
a description and that topic.

## Installing them

```bash
gh auth setup-git
go env -w GOPRIVATE='github.com/<owner>/*'
go get github.com/<owner>/<name>@<tag>

npm install github:<owner>/<name>#<tag>

gh repo clone thealexsan/agent-groundwork ~/.groundwork -- -q 2>/dev/null || git -C ~/.groundwork pull -q
node ~/.groundwork/install.mjs <project> --name "<Name>" --checks "<gate>" --scopes "<a,b>" [--deploys --ops --plans --rules go,nextjs,ui,page-weight]
```

Each part's README is the reference; read it before using the part, not the part's source.

## The stack

| Layer | Default |
|---|---|
| backend | Go, standard library `net/http`, one module, a block (binary, process, port) per area |
| data | PostgreSQL (Neon), sqlc for every query, migrations with `strata`; Redis for cache, sessions and limits |
| web | Next.js App Router, React, TypeScript, Tailwind, and the owner's UI kit and API client parts if there are any |
| hosting | one Linux box: pm2, nginx, Cloudflare in front |
| delivery | GitHub, pull requests, GitHub Actions; `groundwork --ops` for CI and deploy |
| repository | `groundwork` installed on day one |

No layer has a fixed version. Each is taken at its newest stable release, looked up at the moment
it is chosen, never recalled from memory or copied from an older project:

```bash
npm view next version; npm view react version; npm view tailwindcss version; npm view typescript version
curl -s 'https://go.dev/dl/?mode=json' | jq -r '.[0].version'
go list -m github.com/<module>@latest
gh release view -R <owner>/<part> --json tagName --jq .tagName
```

PostgreSQL: the newest major Neon offers when the project is created. Node: the current LTS. A
release candidate, beta or canary is not stable. The lockfile, `go.mod` and the Neon project record
the exact versions; moving an existing project to a newer one is its own pull request, never part
of feature work.

## Leaving the stack

Allowed only when one of these is true, and only for the part that does not fit:

- **The user names another stack and firmly asks for it.** A passing mention is not that.
- **The data does not fit PostgreSQL.** For example: large append-only analytics → ClickHouse;
  data that lives on a device and syncs later → SQLite; vectors and full-text search stay in
  Postgres (pgvector, `tsvector`) until a measured limit says otherwise.
- **The kind of app does not fit.** For example: a native mobile app, a game, embedded or
  desktop software, a data-science notebook, a static site with no backend.

Before building, say in one line which part is replaced, why, and with what. Record it where the
project keeps decisions (`HANDOVER.md` §3, `.agent/decisions.md`). Everything else stays on the
stack and on our parts.
